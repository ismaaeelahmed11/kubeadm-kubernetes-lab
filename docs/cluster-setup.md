# Kubernetes Cluster Setup Guide

## Overview

This document outlines the infrastructure setup and Kubernetes bootstrap process used for the self-managed kubeadm homelab.

The cluster consists of two Ubuntu virtual machines running Kubernetes without a managed cloud service.

## 1. Infrastructure

| Component | Configuration |
|---|---|
| Hypervisor | Oracle VirtualBox |
| Operating system | Ubuntu 26.04.1 LTS |
| Control plane | k8s-control — 192.168.56.10 |
| Worker | k8s-worker — 192.168.56.11 |
| Kubernetes | v1.35.9 |
| Container runtime | containerd 2.2.2 |
| Container networking | Calico v3.31.0 |

Each VM uses two network adapters:

- NAT for outbound internet access.
- Host-only networking for communication between the Windows host and VMs.

Static IP addresses provide predictable cluster connectivity.

## 2. Prepare Both Nodes

Before installing Kubernetes:

1. Configure unique hostnames and node IP addresses.
2. Disable swap.
3. Enable IPv4 forwarding and required kernel networking modules.
4. Install and configure containerd with systemd cgroups.
5. Install kubeadm, kubelet and kubectl from the Kubernetes v1.35 package repository.
6. Verify containerd and kubelet services.

The control-plane VM was provisioned with 2 vCPUs and 3 GB RAM; the worker with 2 vCPUs and 2 GB RAM.

## 3. Initialise the Control Plane

On `k8s-control`, initialise Kubernetes using kubeadm with the control-plane host-only address.

Example:

```bash
sudo kubeadm init \
  --apiserver-advertise-address=192.168.56.10
```

The actual bootstrap configuration must use a pod network CIDR compatible with the chosen Calico configuration.

Configure kubectl using the administrator kubeconfig generated by kubeadm.

Verify API access:

```bash
kubectl get nodes
```

## 4. Install Calico Networking

Install Calico v3.31.0 using its version-specific installation instructions and a pod network configuration matching the kubeadm bootstrap settings.

Verify networking components:

```bash
kubectl get pods -A
kubectl get nodes
```

The control-plane node should reach the `Ready` state after the required networking components become operational.

## 5. Join the Worker Node

On the control plane, generate a fresh worker join command:

```bash
kubeadm token create --print-join-command
```

Run the resulting command with `sudo` on `k8s-worker`.

Check both nodes:

```bash
kubectl get nodes -o wide
```

Expected node names:

- `k8s-control`
- `k8s-worker`

Both nodes should report `Ready`.

Do not commit bootstrap tokens or sensitive kubeconfig files to Git.

## 6. Deploy the Application

From the root of this repository:

```bash
kubectl apply -f manifests/
```

Verify:

```bash
kubectl get deployments
kubectl get pods -o wide
kubectl get services
```

The NGINX Deployment runs four replicas, with ClusterIP and NodePort Services providing application connectivity.

## 7. Validate Application Access

The lab's NodePort Service uses port `32396`.

From the Windows host:

```text
http://192.168.56.11:32396
```

This address requires connectivity to the VirtualBox host-only network.

## 8. Troubleshooting Experience

During implementation, I investigated and resolved several infrastructure and cluster issues:

- VirtualBox CPU lockups and hardware virtualization performance.
- Kubernetes bootstrap and control-plane recovery.
- Kubernetes administrative access and RBAC.
- Networking and cluster component readiness.

See the main README and `screenshots/` directory for supporting evidence.

## Scope

This guide documents the main build stages and verified configuration rather than providing fully automated VM provisioning.

For a fresh build, use the official Kubernetes and Calico documentation for version-specific package installation, bootstrap configuration and networking requirements.

The cluster is a local learning environment with one control-plane node and one worker node, not a production high-availability deployment.
